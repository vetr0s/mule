# MULE

MULE, Multi-Use Library Essentials, is a personal standard library for C.
Each module lives in its own folder under `src/`. `TODO.md` holds the
decisions and the goal of each release. The work itself is tracked in
GitHub issues, one milestone per release.

`CLAUDE.md` is a symlink to this file. Edit `AGENTS.md`.

## Workflow

Agents write the code. The user reviews and merges it, as a senior
engineer reviews a team's pull requests. A ruleset on `main` takes
changes only through a pull request whose CI passed.

1. **Issue.** Start from one. `gh issue list --milestone 0.4.0` lists a
   release's open work, and `gh issue view N` has its acceptance
   criteria. Work without an issue gets one first. Done when you can
   name the issue number.
2. **Branch.** From a current `main`:
   `git switch main && git pull --ff-only && git switch -c N-slug`, with
   the issue number and two or three words.
3. **Commit.** One concern per commit, tests first. Squash merging joins
   the branch's commit messages into the commit on `main`, so each one
   explains why. The last ends its body with `Closes #N`.
4. **Check.** Run `./build format`, then `./build ci` and `./build docs`.
   Done when all three passed after the last commit.
5. **Open the pull request.** `git push -u origin N-slug`, then
   `gh pr create`. The title is the change in the imperative, because it
   becomes the subject of the commit on `main`. The body fills every
   section of `.github/pull_request_template.md`.
6. **Watch CI.** `gh pr checks --watch`. Fix a failure with a new commit
   on the branch. Done when every check is green.
7. **Hand over.** Report the pull request's URL and stop. Merging,
   approving and pushing to `main` belong to the user.
8. **Answer review.** `gh pr view N --comments` lists the comments.
   Answer each with a commit on the branch, or with a reply that says
   why not. Push, then watch CI again.

Keep a pull request to one issue and a diff the user can read in one
sitting. Split one that grows past that.

- File what you find instead of fixing it on the side: a bug, a follow-up
  or a missing test. Give it the milestone of the release that will ship
  it, and one label: `bug`, `enhancement`, `testing`, `documentation` or
  `chore`. An idea with no caller yet gets `parked` and no milestone.
- An issue body states the problem and what done looks like, as a
  check someone could run.

## Commands

The build is `build.c`. Bootstrap it once with `cc -Isrc -o build build.c`.
It rebuilds itself after that, and `./build --help` lists the rest.

- test: `./build test`
- lint: `./build release && ./build docs`
- everything CI runs: `./build ci && ./build docs`
- format: `./build format`
- build: `./build`

## Key directories

- `src/<module>/`: one folder per module. `src/test/` is the test harness.
- `tests/`: one `test_<module>.c` unity file per module.
- `bench/`: benchmarks, built by `./build release`.
- `dist/mule.h`: generated by `./build dist`. Never edit it by hand.
- `.build/`: all build output. `examples/project/` has its own.
- `docs/`, `notes/`: Doxygen inputs and the generated str guide.
- `specs/`, `reviews/`: factory specs and reviews.

## Layout

The folder, include and naming rules live in the file comment of
`src/base/base.h`. Read it before adding, moving or including a file.

## Conventions

- A function that can fail returns `bool`. A failed call leaves its arguments
  byte-for-byte as they were. `check_unchanged_on_oom` in
  `tests/test_str.c` proves this for every `str` operation, so new
  operations join its table.
- A zero-initialised struct is a valid empty value: `Str s = { 0 };`,
  `Arena a = { 0 };`. New types keep that property.
- Code that allocates takes a `const Allocator *`, and null means the heap.
  It allocates through `mem_realloc`. Outside the test harness and `tests/`,
  only `src/mem/` calls libc allocation directly.
- Write a macro only for what a function cannot do: `sizeof` a literal,
  capture `__FILE__` and `__LINE__`, or work for any element type.
- Mark every function whose result must be checked `MULE_NODISCARD`.
- A hot path that stores through `s->data` copies the fields it needs into
  locals first, as `str_push` and `str_append` do. A `char` store may alias
  any field of `*s`, so otherwise the compiler reloads them on every call.
- Targets are Unix with clang 17+ or gcc 13+. A feature missing from either
  goes behind a fallback in `base.h`, the way `ckd_add` does.
- The floor is C11 and the code reads as C99: `NULL`, `{ 0 }`,
  `<stdbool.h>` and the `MULE_` attribute macros in `base.h`. Use C11 only
  where C99 has no spelling, as the arena does for `alignas` and `alignof`.
  `./build release` rejects C23 spellings, because `-Wpedantic` flags them.
- Projects use `dist/mule.h`, which `./build dist` joins from `src/`.
  A new module joins `modules` in `build.c`, after the modules it
  includes. Commit the regenerated `dist/mule.h` with every change to
  `src/`. CI fails when it is stale.

## Tests and docs

- Each module has `tests/test_<module>.c`, a unity file that includes
  `test/test.h` first. `test_init` installs the harness `Allocator` with
  `mem_set_heap`. It counts live allocations through null allocators and arena
  blocks, and `RUN` fails a test that leaks. `test_fail_alloc_after(n)` makes
  those allocations fail on demand. A direct `malloc` in a test is not counted.
- Every public declaration has a doc comment. Examples are regions of the
  test files pulled in with `@snippet`, so every documented example compiles
  and runs.
- Each module header is a Doxygen topic. A `@defgroup mod_<name>` comment at
  the top holds the module's design and rules, `@name` sections group its
  members, and `@}` closes it at the end. `modules` in `build.c` sets the
  order of the topics.
- A function that can fail says what false means under `@return`. Asserts
  go under `@pre`, and pointers it invalidates under `@warning`. Document
  all of a function's parameters or none, because `./build docs` fails on a
  partial set.
- `docs/concepts.md` holds the rules that span modules. A program in
  `examples/` or `notes/str-examples/` joins `docs/examples.dox`, so its
  calls link to the reference. Name an `examples/` program for what it
  does, because Doxygen matches `@example` by basename and `fs.c` would
  collide with a module source.
- `at()` in `tests/scratch.h` returns its buffer. Give each path in one
  call its own buffer, or the call depends on argument evaluation order.
- Watch a new test fail once against a broken implementation before you
  trust it.
- The tests also run under the `release` profile, with `-DNDEBUG`. A check
  that must hold there uses `CHECK` or `log_assert`, not `assert`.
- Under ASan each arena allocation is followed by `MEM_REDZONE_` bytes,
  so a test that checks an arena's `used` adds it. Check poisoning with
  `__asan_region_is_poisoned`, as `test_mem.c` does.
- clang -O2 removes a `malloc` whose result is only compared with null,
  and folds the check to false. A test that expects an allocation to fail
  stores the result through `volatile`, as `libc_oom_leaves_block` does.

## Done

- `./build format --check`, `./build ci` and `./build docs` pass, and
  CI is green on the pull request. `ci` runs the tests under every
  profile, the `-Werror` release build and the examples. `./build docs`
  fails on any undocumented member.
- When a public API changes, `./build examples` still passes. It compiles every
  file in `notes/str-examples/` with `cc -std=c11 -Idist`. `10_dangling.c` and
  `11_double_free.c` are bugs on purpose and only need to compile.
- `notes/str-and-strview.html` is generated. Edit
  `notes/str-and-strview.tmpl.html` or the examples, then run
  `python3 tools/gen-guide.py`. It inlines each example and the
  standard-html stylesheet from `~/.claude/skills/`. Its two sanitizer traces
  quote `mule.h` line numbers, so a change to `src/` can make them stale.
  Re-capture them by running the examples.
- A change a user of the library would notice adds a line under
  `## [Unreleased]` in `CHANGELOG.md`, in the same commit.

## Versions and releases

MULE follows Semantic Versioning 2.0.0. The version lives in the
`MULE_VERSION_*` macros and `MULE_VERSION` in `src/base/base.h`, and
`./build version` prints it. A release marks a milestone the user calls. It
does not happen on every commit.

- Pick the bump from what changed since the last release. While the major
  version is 0, a new module or any change that breaks a caller bumps the
  minor version. A break is a removed or renamed name, a changed signature,
  or changed behaviour a caller relies on. Fixes, docs and additions that
  break nothing bump the patch version. From 1.0.0 on, a break bumps the
  major version, an addition the minor and a fix the patch.
- To release: rename `## [Unreleased]` in `CHANGELOG.md` to
  `## [X.Y.Z] - YYYY-MM-DD`, open a new empty Unreleased section above it,
  and update the links at the bottom. Remove the release's row from
  `TODO.md`. Its milestone must have no open issues: move what is left to
  the next one. Set the version
  macros, run `./build dist`, and check that `./build ci` and
  `./build docs` pass. Open it as a pull request titled
  `Release vX.Y.Z`. Once the user merges it and CI passes on `main`, and
  the user says to, tag that commit with
  `git tag -a vX.Y.Z -m "MULE vX.Y.Z"` and push the tag. A fix that CI
  needs gets its own pull request, and the tag goes on its commit. Close
  the milestone once the release is published.
- The tag starts `.github/workflows/release.yml`. It checks the tag against
  `MULE_VERSION`, runs the tests, and publishes `dist/mule.h` with the
  version's changelog section as the notes.
- Never move or delete a tag that has been pushed. Fix a bad release with a
  new patch release.
- CI publishes the reference to https://mule.vetr0s.dev on every push to
  `main` that passes. It shows `main`, not the last release.

## Known pitfalls

- `str_with_capacity` and `str_from` initialise. They do not free what the
  `Str` already held, so call `str_free` first on a `Str` that owns memory.
- gcc ignores a `(void)` cast on a `MULE_NODISCARD` call, so `-Werror`
  fails there. Free through `mem_realloc` by assigning its null result:
  `p = mem_realloc(a, p, n, 0);`.
- A mark taken before `arena_reset` or `arena_free` is dead. Nothing checks
  it, so restoring it is undefined.
- An `Arena` must stay put once `arena_allocator` has been called. The
  allocator's context points at it.
- Doxygen reads both branches of an `#if`. Wrap internal macros in
  `/** @cond */` and `/** @endcond */`.
- Doxygen links a code span that matches a topic id, and shows the title
  instead. Topic ids carry `mod_` so that `./build test` stays as written.
- Doxygen links a macro only when it is written with `()`, as `arr_push()`.
- `docs/DoxygenLayout.xml` is a whole `doxygen -l` file from 1.18 with one
  change. A partial layout file drops the main page and the navigation, and
  another doxygen version rejects or warns about this one. After upgrading
  doxygen, regenerate it with `doxygen -l` and move the `<group>` overview
  above `<memberdecl>` again.
- Doxygen wants a comment on each member. A `@name` group comment does not
  count, so give each macro a trailing `/**< ... */`.
- Each output keeps the command that built it in `<out>.cmd`, so a
  changed flag rebuilds it. A new set of flags belongs in `profiles` in
  `build.c`, which gives it its own folder, so switching never rebuilds.
- A `build/` directory left by the old Makefile blocks
  `cc -Isrc -o build build.c`. Remove it once.
- CI's Linux runners are x86_64. Docker on an Apple silicon Mac runs arm64
  Linux, so a local gcc pass there can still fail in CI. Code that
  depends on argument evaluation order did exactly that in v0.3.0.
- AddressSanitizer on macOS does not detect leaks, and Apple clang ships no
  libFuzzer. The harness `Allocator` in `test/test.h` covers leaks. Fuzzing
  needs Linux.
- macOS 26 libmalloc keeps a large block grown by realloc dirty after free,
  and never reuses it. `mem_realloc` grows by malloc and copy on Apple for
  that reason. `heap_growth_returns_memory` only runs without ASan, because
  ASan replaces libmalloc. Run `./build test --profile=nosan`
  after touching it.

## Benchmarks

- Compare a change by building the benchmark before and after it, then
  running each binary several times. One run misleads, and a change
  elsewhere can move a micro-benchmark 4x by shifting what gets inlined.
  Explain a shift like that from the disassembly before accepting it.
- Measure memory with `/usr/bin/time -l` on macOS. `bench_corpus` holds the
  input and the rebuilt copy, and peaks near 3.5x its largest file.
- `base.h` sets `_POSIX_C_SOURCE`, which hides BSD extensions on macOS,
  such as `ru_maxrss` in `struct rusage`. Define `_DARWIN_C_SOURCE` before it
  in a scratch probe. `<mach/mach.h>` works without it.
