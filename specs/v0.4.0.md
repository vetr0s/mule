# MULE v0.4.0

## Goal
A testing setup that keeps up as the library grows. Every kind of check is a `./build` profile or command, so CI is a list of `./build` calls and any CI failure reproduces locally with the same command. Checks run in three tiers: every push, nightly, and release. The library's API does not change. The test harness in `src/test/` may grow, because projects use it too. 0.4.0 comes before text, so the text module's parsers are fuzzed from the start.

## The caller: CI, sketched
```yaml
# every push and pull request, under about ten minutes
- run: cc -Isrc -o build build.c
- run: ./build ci
# nightly, on a schedule
- run: ./build ci --tier=nightly
```

## Shape
Profiles are data in `build.c`. Each one builds into `.build/<name>/`.

```c
typedef struct Profile {
    const char *name;               /* output goes to .build/<name>/ */
    const char *cc;                 /* null means $CC */
    const char *const *flags;
    size_t flag_count;
} Profile;
/* debug (ASan+UBSan), nosan, msan, filc, cov, release; tsan joins in 0.6.0 */
```

| Tier | Runs |
| --- | --- |
| Push | Every profile CI can run quickly, the tests, the examples, the consumer builds, 30 to 60 seconds per fuzz target, docs, the dist check. |
| Nightly | Long fuzz runs with the corpus cached, MSan, Fil-C, mutation testing, instruction counts on every benchmark. |
| Release | Everything, then a build of an example against the `mule.h` the workflow just published. |

## Work, in order
1. Profiles in `build.c`, replacing `--no-sanitize` and `--out` for configurations. `./build ci` runs a tier.
2. ASan poisoning for arenas, so an overflow from one arena allocation into the next is reported.
3. Consumer builds: `mule.h` in two files with one defining `MULE_IMPLEMENTATION`, linked together. Built with `-std=c11`, `c17` and `c23`, with `-DLOG_LEVEL_MIN`, and with `-Wall -Werror` on gcc and clang.
4. GitHub annotations: under `GITHUB_ACTIONS`, a failed check also prints `::error file=...,line=...::`.
5. libFuzzer targets in `fuzz/` for `sv_parse_*`, `args_parse`, `build_read_deps`, `str_read_line`, the split and token functions and the path helpers. Each checks properties, such as a round trip or an unchanged argument after a failure. A crash becomes a committed regression input. A nightly workflow runs them long.
6. An MSan profile. Clang on Linux only.
7. A Fil-C trial by hand, then a nightly profile if it earns one.
8. Allocation budgets in unit tests, such as n appends making at most about log2(n) allocations.
9. Instruction counts: benchmarks under cachegrind on Linux against a committed baseline, failing past a threshold.
10. `./build bench-compare <ref>` for wall clock on a quiet machine, never in CI.
11. `./build mutate <file>` and a `cov` profile with `./build coverage`. Both are review aids, not gates.
12. A golden output: `main.c` on `data/pg2554.txt` prints 208532 words and 9917 unique.

## Open
- Installing the Fil-C toolchain and valgrind in CI each needs the user's yes. libFuzzer and MSan come with clang.

## Acceptance criteria
1. CI's workflow steps are `./build` calls, and each passes locally with the same arguments.
2. Switching profiles never rebuilds another profile's outputs.
3. A test that writes one byte past an arena allocation fails under the debug profile.
4. The two-file consumer build links on gcc and clang under each standard.
5. A failed check in CI shows on the pull request diff at its file and line.
6. Each fuzz target runs in the push tier and finds a planted bug in its function within the push budget.
7. The nightly workflow runs on a schedule and reports each job.
8. A benchmark change that adds 5% more instructions fails the instruction-count check.

## Out of scope
- TSan, which comes with threads in 0.6.0.
- Valgrind memcheck. ASan, MSan and Fil-C cover it.
- Wall-clock timing gates in CI. Shared runners are too noisy for them.
